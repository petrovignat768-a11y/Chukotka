# Лабораторная работа 2. Модульное тестирование для Java

## Цель и условия

Освоить документирование публичных методов и модульное тестирование Java с JUnit: отделить логику от представления, проверить результаты и состояние при типовых и граничных входных данных, сформировать отчёты о запуске и покрытии.

Исходные материалы: учебник, печатные страницы 62–68 и 80–81; спецификация пользователя `lab-7/original/Specification.md`; описание `lab-7/original/readme.md`. В предоставленном репозитории есть Windows EXE, документация и изображение; исходного кода приложения нет, хотя README упоминает `todo_app.py`. Поэтому создана **самостоятельная Java-модель по текстовой спецификации**. Это не исходный код EXE и не тестирование EXE; совпадение поведения бинарного приложения с моделью не установлено.

Среда фактического запуска: Linux, OpenJDK `21.0.13.0.3`, Maven `3.8.7`; компиляция с `--release 17`. В проекте используются JUnit Jupiter `5.10.2`, Maven Surefire `3.2.5`, JaCoCo `0.8.12`. На JDK 17 непосредственно запуск не проводился.

## Связь с учебником

* Стр. 62–65: JUnit подключён через Maven; тесты с `@Test` обнаруживает Surefire. `@BeforeEach` создаёт новый объект для каждого тестового случая, проверки выполнены посредством `assertEquals`, `assertTrue`, `assertFalse` и других assertions. Есть параметризованные сценарии с разными данными. Очистка через `@AfterEach` не нужна, поскольку внешние ресурсы тесты не используют.
* Стр. 66–68: неверные числовые индексы проверяются через `assertThrows`, в том числе проверяется текст исключения; свойства результата проверяются совместно через `assertAll`.
* Стр. 80–81: выделена логика отдельно от UI, описаны все публичные методы, проверяются возвращаемые значения и состояние. Учебник отдельно предусматривает команды, передачу собственного проекта другому студенту, проверку документации, тестирование чужого проекта по документации без чтения кода и оценку его качества. **Эти коллективные этапы не выполнялись**: проекта и документации другого участника не предоставлено, проверки другим студентом и рецензии не было, чужой проект не оценивался. Здесь тесты создавались вместе с собственной моделью, поэтому независимым тестированием «вслепую» они не являются.

## Архитектура и спецификация модели

`src/main/java/ru/petrov/tasktracker/TaskTracker.java` содержит публичный `TaskTracker` и вложенные типы `Task`, `Result`, `Outcome`; зависимости от UI отсутствуют. Трекер содержит список неизменяемых задач в памяти; `getTasks()` возвращает неизменяемый снимок, не меняющийся при дальнейших действиях. `Task` отдаёт исходный текст, признак выполнения и строку с префиксом `[ ] ` либо `[✓] `. `Result` сообщает код, уведомление, успешность и необходимость очистить поле ввода; реально очистить поле должен интерфейс.

| Действие по спецификации | Контракт модели и инвариант |
|---|---|
| Добавление | `addTask(text)` добавляет задачу в конец со статусом «не выполнена», возвращает `ADDED` и признак очистки поля. Если текст пустой или пробельный, `INVALID_TEXT` и точное сообщение `Текст задачи не может быть пустым!`; список не меняется. |
| Выполнение | `completeTask(index)` меняет только статус выбранной задачи, не меняет количество и порядок. Если выбор отсутствует — `NO_SELECTION`, `Выберите задачу из списка!`. Если она уже выполнена — `ALREADY_COMPLETED`, `Эта задача уже выполнена`; повторная операция не меняет состояние. |
| Удаление | `deleteTask(index)` удаляет выбранную задачу, сохраняя относительный порядок и данные остальных; возвращает `DELETED`. Если выбор отсутствует — `NO_SELECTION`, `Выберите задачу для удаления!`, без изменения списка. |

Допущения модели там, где спецификация не устанавливает контракт программного API:

1. `null` как текст считается пустым. Строка пробельная, если она пуста или каждая кодовая точка удовлетворяет `Character.isWhitespace` **или** `Character.isSpaceChar`; например, `U+00A0` отклоняется. Не все невидимые форматные символы являются пробелами: `U+200B` принимается. Данная классификация — решение модели, не проверенное на EXE.
2. Валидный текст сохраняется полностью, в том числе начальные и конечные пробелы; дубликаты разрешены и обрабатываются независимо по текущему индексу.
3. `null` как индекс означает отсутствие выделения. Числовые индексы начинаются с нуля; индекс за пределами `[0, размер)` даёт `IndexOutOfBoundsException` с сообщением `Индекс задачи вне диапазона: N`, без изменения состояния. Вызывающий интерфейс должен отслеживать актуальность индексов.
4. Успешная операция возвращает пустое сообщение; только успешное добавление возвращает `shouldClearInput() == true`. Успешны только коды `ADDED`, `COMPLETED`, `DELETED`.

Полный публичный контракт и пример использования — [README.md](README.md); сгенерированная документация по всем открытым классам и методам — [Javadoc](docs/api/index.html). UI, модальные окна и файловое хранение не реализованы; модель не потокобезопасна.

## Индивидуальные сценарии и тесты

Все сценарии реализованы в [TaskTrackerTest.java](src/test/java/ru/petrov/tasktracker/TaskTrackerTest.java). `result(...)` совместно проверяет открытые методы результата (`getOutcome`, `getMessage`, `isSuccess`, `shouldClearInput`), в том числе точные сообщения и сигнал для UI.

| Сценарий | Ожидаемый результат и проверка |
|---|---|
| Создание экземпляра | `newTrackerIsEmpty`: пустой список; `separateTrackersDoNotShareState`: экземпляры не влияют друг на друга. |
| Добавление обычной задачи | `addCreatesUncompletedTaskWithExactPrefixAndSuccessResult`: правильный код и флаг очистки, текст, статус, префикс и размер списка. |
| Добавление к существующим | `addAppendsWithoutChangingPreviousTextOrderOrStatus`: добавление в конец; прежний выполненный статус и порядок сохраняются; крайние пробелы текста не теряются. |
| Пустые данные | `blankInputIsRejectedWithoutChangingExistingTasks`: `null`, `""`, пробелы, табуляция, переводы строки, `U+00A0`, `U+2003`; точное предупреждение, флаги отказа, состояние со смешанными статусами неизменно. |
| Непустые данные | `nonblankTextIsPreservedExactly`: одиночные символы, текст с пробелами, кириллица, emoji, текст, похожий на префикс статуса, `U+200B`; текст и отображение сохраняются точно. `longTaskIsNotTruncated`: длинная строка не обрезается. |
| Отметка первой, средней, последней | `completeFirstMiddleOrLastChangesOnlySelectedTask`: три позиции, правильные статус/префикс выбранной задачи и результат, инварианты текста, порядка, количества остальных. |
| Нет выбора при отметке | `completeWithoutSelectionOnEmptyListWarnsAndDoesNotMutate`, `completeWithoutSelectionOnNonemptyListWarnsAndDoesNotMutate`: на пустом и непустом списке возвращается точное предупреждение без изменений. |
| Повторная отметка | `completingAlreadyCompletedTaskWarnsWithoutChangingAnything`: точное сообщение и неизменность всех задач. |
| Ошибочный индекс отметки | `invalidCompleteIndexThrowsAndKeepsState`: отрицательный, равный размеру, больше размера, минимум и максимум `int`; тип и текст исключения, сохранность состояния. |
| Удаление первой, средней, последней | `deleteFirstMiddleOrLastPreservesRemainingOrderTextAndStatus`: правильный размер и сохранение текста/статуса и порядка оставшихся, в том числе выполненной задачи. |
| Нет выбора при удалении | `deleteWithoutSelectionOnEmptyListWarnsAndDoesNotMutate`, `deleteWithoutSelectionOnNonemptyListWarnsAndDoesNotMutate`: точное предупреждение и отсутствие изменений. |
| Ошибочный индекс удаления | `invalidDeleteIndexThrowsAndKeepsState`: те же граничные индексы, исключение и состояние. `indexZeroOnEmptyListIsNotTheSameAsNoSelection` проверяет нулевой индекс пустого списка для обеих операций. |
| Дубликаты и сдвиг индексов | `duplicateTextsAreIndependentAndDeletionUsesSelectedIndex`, `sequentialOperationsUseCurrentIndicesAfterDeletion`: одинаковые тексты не смешиваются, последующие операции используют новые индексы. |
| Снимки | `snapshotsAndTaskValuesAreImmutableAndDoNotTrackLaterChanges`: внешняя модификация списка запрещена; ранее полученный список и значение задачи не меняются после выполнения, добавления и удаления. |
| Перечисление кодов | `outcomeEnumerationProvidesStableNames`: `values()`, `valueOf()` и ошибки при неизвестном и `null` именах. |

Тесты проверяют все объявленные операции модели и аксессоры, а также предусмотренные условия и сообщения; полный перебор всех возможных входных строк не проводился.

## Воспроизведение

```bash
cd lab-2
set -o pipefail
mvn -B -ntp -Dmaven.repo.local="$PWD/.m2/repository" clean test 2>&1 | tee logs/maven-test.log

# При необходимости пересоздать HTML API-документацию:
javadoc -encoding UTF-8 -docencoding UTF-8 -charset UTF-8 \
  -d docs/api src/main/java/ru/petrov/tasktracker/TaskTracker.java \
  2>&1 | tee logs/javadoc.log
```

Команды рассчитаны на Bash, JDK 17+ и Maven 3.8+; при отсутствии локально загруженных зависимостей нужен доступ к Maven Central. `clean` исключает накопление данных покрытия от предыдущих прогонов. Зависимости при этих командах сохраняются в локальную папку `.m2/repository` данного проекта.

## Вывод и оставшиеся ограничения

Логика трёх действий реализована отдельно от интерфейса; тесты подтвердили соответствие созданной модели приведённому контракту на выбранных данных, включая проверку сообщений, статусов, границ и инвариантов. Реальный запуск и покрытие сохранены, но успешные модульные тесты не удостоверяют работу приложения в целом.

Не проверены исходный Windows EXE, его реальные окна и очистка текстового поля, визуальное выделение, интеграция и поведение пользовательского интерфейса. Модель не поддерживает сохранение между запусками, многопоточность, совместимость с неизвестными внутренними форматами EXE; контракт пробелов, недопустимых индексов и неизменяемых снимков является добавленным решением. Коллективная передача, независимая оценка документации и рецензирование чужого проекта, предусмотренные заданием учебника, не выполнены и остаются на участников группы.
