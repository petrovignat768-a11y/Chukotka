# Лабораторная работа № 3
## Модульное тестирование для .NET-языков

### Цель и исходные условия

Освоить выделение логики из представления и проверку публичного контракта модульными тестами: исследовать допустимые и граничные данные, ошибки и инварианты. Исходное задание — трекер задач по `lab-7/original/Specification.md`; использован также `lab-7/original/readme.md`. В предоставленном репозитории есть Windows EXE, документация и изображение; упомянутый в README Python-исходник отсутствует.

**Объект проверки — самостоятельно написанная учебная модель на C#/.NET, а не исходный EXE.** Приложение `todo_app.exe` не запускалось и не тестировалось, его реальное соответствие спецификации неизвестно. Модель переносит описанную функциональность в публичный программный интерфейс и явно фиксирует дополнительные соглашения, необходимые для тестов.

### Связь с учебником

В разделе 3.5.2, печатные стр. 68–72 (стр. 73 уже начинает раздел о GoogleTest), описаны NUnit/MSTest, отдельный тестовый проект со ссылкой на проверяемый, `[TestMethod]`, `[TestInitialize]`, проверки `Assert` и тестирование исключений; особо отмечено, что тесты следует выводить из спецификации. Здесь использован **MSTest 3.6.4**, названный в учебнике фреймворк, с `Microsoft.NET.Test.Sdk 17.12.0` и `coverlet.collector 6.0.2` для измерения покрытия. Фикстура создаёт новый объект перед каждым методом; параметризованные `[DataTestMethod]`/`[DataRow]` проверяют несколько значений. Исключения проверяются `Assert.ThrowsException` вместо приведённого в учебнике атрибута `ExpectedException`.

Общие рекомендации стр. 79 — независимость от UI и границы — и задание стр. 80–81 учтены в пределах доступного: публичные методы описаны и проверены по контракту. Однако групповая часть, передача и проверка **чужого** проекта в команде, независимая оценка документации и звёздная оценка чужого кода **не выполнены**: участники и чужой проект не предоставлены. Это индивидуальная работа; автор модели и тестов один, поэтому независимое «слепое» тестирование чужой реализации не имитируется. Тестовые ожидания выведены из пользовательской спецификации и оговорённых дополнений модели.

### Архитектура и контракт

Решение `Lab3.sln` состоит из `src/TaskTracker` (библиотека логики) и `tests/TaskTracker.Tests` (отдельный тестовый проект со ссылкой `ProjectReference` на библиотеку). Код не зависит от окон, файловой системы или сети; NuGet нужен лишь для восстановления тестовых пакетов.

- `TaskTracker` содержит упорядоченный список, изначально пустой; `AddTask`, `CompleteTask`, `DeleteTask` выполняют действия, `GetTasks` возвращает неизменяемый снимок.
- `TaskEntry` хранит текст и статус, а `DisplayText` выдаёт префикс `[ ] ` или `[✓] `. `OperationResult` содержит код, предупреждение и признак необходимости очистить поле. Реальное поле и модальные окна не реализованы.
- Контракт каждого метода, тексты сообщений, исключения и дополнительные соглашения приведены в [SPECIFICATION.md](SPECIFICATION.md). Документация XML, **фактически сгенерированная компилятором** из XML-комментариев, сохранена в [docs/TaskTracker.xml](docs/TaskTracker.xml); это документация своего проекта. При сборке она также создаётся в `src/TaskTracker/bin/Release/net8.0/TaskTracker.xml`.

Допущения, не установленные спецификацией EXE: `null` означает отсутствие выделения; переданный индекс вне списка возбуждает `ArgumentOutOfRangeException` (в том числе 0 для пустого списка). `null` и все строки, распознаваемые `string.IsNullOrWhiteSpace`, отклоняются; непустой текст сохраняется без обрезки, дубликаты допустимы. Это правила **модели**, а не утверждения о приложении. Графическая очистка поля моделируется только через `ShouldClearInput`, диалог — текстом `Message`.

### Воспроизведение

Требуются .NET SDK 8.0 (конфигурация `global.json` допускает подходящие более новые feature-блоки 8.0) и доступ к NuGet для первоначального восстановления пакетов. На выполненной машине использован SDK **8.0.428**, runtime **8.0.34**, Linux x64. Проект можно открыть в Visual Studio; тесты — в Test Explorer.

В Bash из корня распакованного комплекта:

```bash
cd lab-3
./run-tests.sh
# При другом расположении SDK:
# DOTNET=/путь/к/dotnet ./run-tests.sh
```

Скрипт запускает `dotnet test Lab3.sln -c Release --logger 'trx;LogFileName=lab3.trx' --results-directory TestResults --collect 'XPlat Code Coverage' --verbosity normal`. Он размещает домашние и NuGet-кэши под папкой лабораторной работы; при повторном запуске `logs/dotnet-test.log` и `TestResults/lab3.trx` перезаписываются, а сборщик может создать новый каталог отчёта покрытия. Снимок текущего покрытия в `docs/coverage.cobertura.xml` скриптом автоматически не перезаписывается. Через `dotnet test` те же параметры можно применить вручную на другой платформе.

### Выводы и оставшиеся ограничения

На описанных входах все публичные методы модели, статусы, предупреждения, границы, исключения и основные инварианты прошли проверку. Разделение модели и интерфейса позволяет запускать проверки без Windows и GUI; тесты демонстрируют проверку поведения по документированному контракту.

Ограничения: исполняемый оригинал и его GUI не проверены; нет тестов реального очищения поля, диалогов, размера окна, выбора мышью и совместимости с Windows. Поведение вне явно документированных правил модели (например, объёмные данные или потокобезопасность) не гарантировано. Совпадение модели со спецификацией не означает совпадение её с EXE. Не выполнены коллективное рецензирование и оценка чужого проекта, требуемые учебником; их можно выполнить лишь после предоставления участников и отдельного проекта.
