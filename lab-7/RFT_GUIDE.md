# Инструкция для реального IBM Rational Functional Tester

**Статус: инструкция не выполнена.** Установленного IBM RFT и подходящей среды запуска приложения в текущем Linux не обнаружено. Здесь нет сгенерированной RFT object map, записанного сценария или реальных RFT-журналов. Шаблон `rft_support/RFT_INSERT.txt` намеренно неполный и не является готовым тестом.

## 1. Подготовить стенд и выяснить применимость RFT

1. Получите Windows x64 и совместимую лицензионную установку RFT с **Functional Test perspective**, не предполагая, что пользовательская версия работает одинаково с описанной в учебнике 9.1. Зафиксируйте версии Windows, RFT, Java, языка ОС, масштабирования и раскладки. Доступность пробной версии уточняется у поставщика; в этом задании установка не проводилась.
2. Проверяйте в одноразовом тестовом профиле с отдельным рабочим каталогом и резервной копией данных: очистка задач может удалить существующие пользовательские данные. Перенесите в этот каталог копию `lab-7/original/todo_app.exe` и проверьте SHA-256 `e26ad6b44c6fa10fe0341f3417a458784f4481e5a7adc9a95e8d6b470ee974ac`; на Windows: `Get-FileHash .\todo_app.exe -Algorithm SHA256`.
3. Один раз вручную запустите копию, чтобы проверить работу окна, языка и масштабирования, но не считайте это RFT-прогоном. До записи закройте лишние экземпляры. Убедитесь, что состояние тестового списка точно известно; при сохранённом состоянии удаляйте записи только в изолированной копии профиля.
4. В RFT создайте проект функциональных тестов Java. Откройте **Configure Applications for Testing → Add → Executable or Batch File**, укажите путь к копии EXE, рабочую папку и при необходимости аргументы. Имена команд зависят от версии. В JRE/Java-активации нуждается именно Java-приложение; для Windows EXE не объявляйте его Java-программой лишь потому, что RFT-скрипт написан на Java.
5. Проверьте Object Finder/Inspector: распознаются ли поле ввода, кнопки, список и предупреждения как отдельные объекты. Поиск в строках PE выявил признаки PyInstaller и компонентов Tcl/Tk, но не является доказательством поддержки конкретных Tk-элементов в RFT. Если всё окно видно только как изображение или неизвестный объект, зафиксируйте это; не утверждайте, что полноценная проверка Listbox сработала. Проверку требований о чтении интерфейса и хранилища нельзя заменить одним лишь кликом по координатам.

## 2. Записать несколько разных сценариев

1. Для `F02` нажмите **Record a Functional Test Script**, задайте проект и имя, на панели записи выберите **Start Application**, откройте настроенное приложение. Введите `Купить хлеб` и нажмите «Добавить задачу».
2. Во время записи используйте **Insert Verification Point or Action Command → Data/Properties Verification Point** и Object Finder для наблюдаемого списка и поля. Снимайте точки после действия: список содержит `[ ] Купить хлеб`, поле пустое. Значения сопоставляйте со спецификацией, а не считайте автоматически правильными все записанные данные. Удостоверьтесь, что точка охватывает все нужные строки и доступна в воспроизведении. Остановите запись; RFT создаст Java-сценарий и object map. Переименуйте реальные объекты понятными именами. Пример из учебника `orderTable().performTest(orderTable_selectedVP());` относится к его демоприложению, а не к данному EXE.
3. Аналогично запишите отдельные сценарии для `F06` (пустой ввод и точный текст модального предупреждения), `F10` (отметка выбранной средней строки), `F11` (повторная отметка), `F15` (удаление выбранной строки), `F17` (удаление без выбора). Начальное состояние и действия по возвращению к нему запишите явно. Проверяйте количество, порядок, текст и статусы **всех** строк, а не только факт появления списка. Дубликаты отличайте индексом, а не текстом.
4. Сначала воспроизведите каждый записанный сценарий с его константными данными. Сохраните собственные автоматически полученные файлы карты, точки, журнал и при наличии реальные снимки экрана. Несовпадение — FAIL; объект не распознан или тест не дошёл до проверки — BLOCKED/ERROR, но не PASS. Дату, версию и точный контекст указывайте в журнале.
5. RFT может потребовать подходящей раскладки и настроек кодировки для кириллицы. Если при воспроизведении RFT преобразует ввод, сначала проверьте фактический введённый текст через свойство поля; проблема инструмента — не доказательство ошибки приложения. Убедитесь, что в тесте не остаются дополнительные экземпляры приложения.

## 3. Пул данных и программные проверки

1. Импортируйте `data/positive.csv` как Test Datapool с первой строкой в качестве имён столбцов (учебник, с. 124–126), выбрав корректную UTF-8-кодировку; откройте пул и проверьте кириллицу, запятую и двойные кавычки. В зависимости от версии формат и названия диалогов могут отличаться. Пустые строки и пробелы в `negative.csv` при импорте могут обрезаться: проверьте фактические значения; иначе в сценарии задайте их явно и проверьте поле перед нажатием.
2. Свяжите пул с записанным скриптом. Через поиск литералов замените только введённый текст на `dpString("taskText")`; затем включите все **12 записей**. По учебнику при повторении скрипта не следует запускать новый экземпляр на каждой строке: либо запускать приложение один раз вручную, убрав автоматический старт из повторяемой части, либо организовать отдельные setup/teardown без неоднозначности. В каждой итерации удалить **именно добавленную** строку и проверить восстановление начального списка; альтернативно перезапускать в подтверждённое чистое состояние. Тест на дубликаты `F05` выполняется отдельно с двумя записями одновременно, поскольку D09 и D10 при очистке между итерациями дубликаты в одном списке не проверяют.
3. Импортируйте `rft_support/lab7/oracle/TodoAssertions.java` в исходники RFT-проекта, сохранив пакет `lab7.oracle` и UTF-8. Используйте инструкции `rft_support/RFT_INSERT.txt`: реализуйте фактические чтение строк списка, текста поля и диалога через возможности **реально распознанных объектов**, используя Object Inspector и документацию установленной версии. Шаблон содержит TODO, а не обещание готовой карты. Перед действием снимите полную копию строк; после — вызовите `assertAdded`, `assertMarked`, `assertDeleted` или `assertUnchanged`; точный текст поля/предупреждения сравните `assertText`.
4. Ошибка `AssertionError` должна стать неуспешным результатом в журнале RFT; экспериментально проверьте, как это делает используемая версия, и при необходимости используйте штатный API сообщения о сбое, не подавляя исключение. Ожидаемый список строится оракулом из **до-действия** и тестового входа; полученный список читается независимо из GUI. Если полные строки недоступны, не подменяйте их ожидаемыми значениями и зафиксируйте BLOCKED.
5. Проверьте `F20`: начать с проверенного пустого списка, записанное добавление обернуть в цикл `1..100` с `String.format("Mass-%03d", i)`, после каждой операции читать действительный список, проверять инвариант и очистку поля, в конце проверить все 100 строк и порядок относительно `data/mass_100.csv`. Пул из 100 итераций без накопления — иной тест. При накоплении обеспечить запуск приложения один раз и не удалять каждую запись до проверки полного итогового списка. После проверки очистить только изолированную тестовую среду.
6. Учебник требует дополнительно читать результирующее хранилище. Проведите исследование по `STORAGE.md`; если оно найдено, дополните программную проверку независимым чтением подтверждённого хранилища. Если оно не найдено или приложение его не использует, зафиксируйте границу исследования и невозможность этого обязательного пункта; не придумывайте файл или базу.
